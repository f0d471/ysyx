# BUG-01　vsnprintf：格式串以 `%` 结尾会扫出字符串之外

| 项 | 值 |
| --- | --- |
| 文件 | `abstract-machine/klib/src/stdio.c` |
| 函数 | `vsnprintf()` |
| 缺陷类型 | 越界读（out-of-bounds read）／潜在无限循环 |
| 严重度 | 🔴 高——静默，症状与病灶完全无关 |
| 引入于 | `0168dce` "device"（PA2 写 klib 时） |
| 发现于 | 2026-07-27 abstract-machine 全量复盘 |

---

## 一、题目

下面这段解析循环，找出它在什么输入下会读到字符串以外的内存。

```c
while (*fmt) {
  if (*fmt != '%') {
    append_char(out, n, &pos, *fmt++);
    continue;
  }

  fmt++;                    // ← 吃掉 '%'

  char pad = ' ';
  if (*fmt == '0') { pad = '0'; fmt++; }

  int width = 0;
  while (*fmt >= '0' && *fmt <= '9') { width = width * 10 + (*fmt - '0'); fmt++; }

  switch (*fmt) {
    case 'd': { ... break; }
    case 'x':
    case 'p': { ... break; }
    case 's': { ... break; }
    case 'c': { ... break; }
    case '%': { append_char(out, n, &pos, '%'); break; }
    default:
      append_char(out, n, &pos, '%');
      append_char(out, n, &pos, *fmt);
  }
  fmt++;                    // ← 吃掉转换符
}
```

<details>
<summary>答案</summary>

任何**以单个 `%` 结尾**的格式串，例如 `printf("progress: 100%")`。

</details>

---

## 二、最小复现

```c
printf("100%");        // 注意是一个 %，不是 %%
char buf[64];
snprintf(buf, sizeof(buf), "50%");
```

---

## 三、原理：指针是怎么跑出去的

关键在于**这个循环有两个 `fmt++`，而它们对"字符串已经结束"这件事的假设不一致**。

以 `fmt = "100%"` 为例，逐步走一遍：

| 步骤 | `fmt` 指向 | 说明 |
| --- | --- | --- |
| 1 | `'1'` `'0'` `'0'` | 走 `if (*fmt != '%')` 分支，正常输出 |
| 2 | `'%'` | 进入格式解析，`fmt++` |
| 3 | `'\0'` | **已经是终止符了**，但代码毫不知情 |
| 4 | `'\0'` | `if (*fmt == '0')`：`'\0'` 不是字符 `'0'`（0x00 vs 0x30），不进 |
| 5 | `'\0'` | 宽度循环：`'\0' >= '0'` 为假，不进 |
| 6 | `'\0'` | `switch ('\0')` → 没有任何 case 匹配 → 落到 `default` |
| 7 | `'\0'` | `default` 输出 `'%'`，再输出 `*fmt`，也就是**把一个 `'\0'` 追加进输出缓冲区** |
| 8 | `'\0'+1` | 末尾 `fmt++` → **指针跨过了终止符** |
| 9 | ？ | `while (*fmt)` 检查字符串**之外**的那个字节 |

从第 9 步起，程序在读别人的内存。会发生什么完全取决于运气：

- 字符串常量后面恰好紧跟另一个字符串的首字节非零 → 把邻居的内容也打印出来（信息泄漏式的乱码）；
- 后面是一大片非零数据 → 一直打印到偶然撞上 `0x00` 为止；
- 格式串位于 `.rodata` 末尾、后面是未映射页 → **访存异常**。在 NPC 上表现为 `mcause` 报 load access fault，而 PC 会停在 `vsnprintf` 里 —— 你会以为是 CPU 取数逻辑写错了，实际上是这行 `fmt++`。

> 💡 **这就是它难查的原因**：崩溃点（`vsnprintf`／访存异常）离病因（某个业务代码里手滑写了 `%` 而不是 `%%`）非常远，而且是否发作取决于链接器把这个字符串放在了哪儿——**换一个 commit、多加一行无关代码，症状就会变或者消失**。

顺带一提，第 7 步往缓冲区写 `'\0'` 本身也是个次生问题：调用者后续对 `out` 做 `strlen` 会在这里提前截断。

## 四、修复

```c
default:
  append_char(out, n, &pos, '%');
  // 格式串在 '%' 之后就结束了：此时 *fmt 已经是 '\0'，不能再 fmt++ 跨过终止符，
  // 否则外层 while 会继续扫描字符串之外的内存。continue 交给外层条件退出循环。
  if (*fmt == '\0') continue;
  append_char(out, n, &pos, *fmt);
```

两个要点：

1. **`continue` 而不是 `break`。** `break` 只跳出 `switch`，控制流仍会落到底下的 `fmt++`，等于没修。`continue` 直接回到 `while (*fmt)`，此时 `*fmt == '\0'`，循环自然结束。这是 C 里 `switch` 嵌在循环中的经典陷阱。
2. **保留那个 `'%'` 的输出。** C 标准把 `"%"` 结尾定义为未定义行为，各家实现不一（glibc 什么都不输出，musl 输出 `%`）。这里选择输出——因为对使用者来说，`printf("100%")` 屏幕上看到 `100%` 比看到 `100` 更符合直觉，也更容易让人意识到自己漏写了一个 `%`。

---

## 五、为什么不在别处修

考虑过在 `fmt++`（第 85 行，吃掉 `%` 那次）之后立刻加 `if (*fmt == '\0') break;`。不采用，因为：

- 它把"处理字符串结束"的责任放在了解析**开始**的位置，而真正需要它的是解析**结束**的位置——中间还隔着 flag 解析和宽度解析两段代码，将来任何人往中间插新的解析逻辑（比如加 `%-` 左对齐、加 `%.3f` 精度），都必须重新想一遍"我这一段会不会走到 `\0`"。
- 放在 `default` 里则天然覆盖了所有半截情况：`"%"`、`"%0"`、`"%12"`、`"%08"` 全部落到同一个 `default`，一处修完。

## 六、举一反三

这个 bug 的抽象形式是：**在一个"逐字符前进"的状态机里，只在循环入口检查了终止条件，却在循环体内部无条件前进了多次。**

自查清单——写任何解析器（不只是 printf）时问自己：

- [ ] 循环体内 `p++` 出现了几次？每一次之前，是否都能保证 `*p != '\0'`？
- [ ] 有没有"消费 N 个字符"的分支，而输入可能只剩 M < N 个？
- [ ] `switch` 里的 `default` 分支，是否考虑了"输入提前结束"这个 case，而不只是"遇到不认识的字符"？

本仓库内的同类高危位置（后续复盘时重点看）：

- `nemu/src/monitor/sdb/` 的表达式求值——词法分析同样是逐字符前进；
- `npc/csrc/` 里所有解析 ELF／命令行的地方；
- 未来实现 `sscanf` 时，格式串和输入串**两个**指针都有这个问题。

## 七、遗留（本次未处理）

`vsnprintf` 还有几处与本 bug 无关、但同属"格式串解析不完整"的缺口，记在这里备查：

- 不支持 `%u`（无符号十进制）。目前会走 `default` 原样打出 `%u`，静默错误。
- 不支持 `%ld` / `%lld` / `%zu` 等长度修饰符。
- `%p` 与 `%x` 共用一个 case，不输出 `0x` 前缀，且按 `unsigned int` 取参——只在 RV32 上恰好正确。
- 不支持 `-`（左对齐）、`+`、`#` 等 flag。

这些是"没实现"而不是"实现错了"，等真正有调用方需要时再补。但 **`%u` 建议尽快补**，因为它长得太像 `%d`，写错了不会有任何提示。
