# BUG-05　atoi：不识别正负号，`atoi("-5")` 返回 0

| 项 | 值 |
| --- | --- |
| 文件 | `abstract-machine/klib/src/stdlib.c` |
| 函数 | `atoi()` |
| 缺陷类型 | 功能不完整 → 静默返回错误值 |
| 严重度 | 🟠 中——错得很安静 |
| 引入于 | **上游** `c04da8c`（NJU-ProjectN 官方骨架自带，非自己写的） |
| 发现于 | 2026-07-27 abstract-machine 全量复盘 |

---

## 一、题目

```c
int atoi(const char *nptr) {
  int x = 0;
  while (*nptr == ' ') { nptr++; }
  while (*nptr >= '0' && *nptr <= '9') {
    x = x * 10 + *nptr - '0';
    nptr++;
  }
  return x;
}
```

找出它与标准 `atoi` 的两处行为差异。

<details>
<summary>答案</summary>

1. **不识别 `'+'` / `'-'` 符号**：`atoi("-5")` 返回 `0` 而不是 `-5`；
2. **跳过的空白字符不全**：只跳空格，不跳 `\t` `\n` `\v` `\f` `\r`。`atoi("\t42")` 返回 `0`。

</details>

## 三、原理：为什么这个 bug 特别安静

### 3.1 失败形态是"返回 0"，而不是报错

```c
atoi("-5")   → 0        // 而不是 -5
atoi("abc")  → 0        // 标准也是 0，无法区分
atoi("0")    → 0        // 合法输入也是 0，更无法区分
```

调用方拿到 `0` 时**没有任何办法判断**这是"解析出的真值"、"解析失败"还是"符号没被认出来"。`atoi` 的接口设计本身就不提供错误通道——这是 C 标准库的历史遗留（正因如此，现代 C 推荐用 `strtol`，它通过 `endptr` 和 `errno` 报告失败）。

### 3.2 它在什么场合会咬人

`atoi` 在这个项目里的主要使用场景是**解析命令行参数和配置字符串**：

- `nanos-lite` / `navy-apps` 里从 `mainargs` 取参数；
- 未来实现 shell 或调试器命令时解析用户输入；
- 任何从字符串读配置的地方。

一旦有人传了负数（坐标偏移、温度、相对跳转量……），你会得到一个 `0`，然后程序带着这个 `0` 一路跑下去，在很远的地方表现为"逻辑不对"。

### 3.3 `'\t'` 那一半为什么也重要

命令行参数经过 shell、Makefile、`MAINARGS` 宏几层传递，混进制表符完全可能。而且 `atoi("\t42")` 返回 0 的失败形态和上面一模一样——安静。

## 四、修复

```c
// 将十进制字符串转换为 int，跳过前导空白，识别可选的 '+' / '-' 符号
int atoi(const char *nptr) {
  int x = 0;
  int neg = 0;

  // isspace() 的全集：空格与 \t \n \v \f \r（后者在 ASCII 中是连续的 0x09~0x0d）
  while (*nptr == ' ' || (*nptr >= '\t' && *nptr <= '\r')) { nptr++; }

  if (*nptr == '-' || *nptr == '+') {
    neg = (*nptr == '-');
    nptr++;
  }

  while (*nptr >= '0' && *nptr <= '9') {
    x = x * 10 + *nptr - '0';
    nptr++;
  }

  return neg ? -x : x;
}
```

几个细节：

- **`'\t' <= c && c <= '\r'` 这个技巧**：ASCII 里 `\t`(0x09) `\n`(0x0a) `\v`(0x0b) `\f`(0x0c) `\r`(0x0d) 恰好连续，一个区间判断顶五个比较。空格(0x20)不连续所以单列。这正是 libc 里 `isspace()` 的实现方式。
- **符号只允许出现一次，且必须紧跟在空白之后**——这是标准行为。`atoi("- 5")` 和 `atoi("--5")` 都返回 0，是对的。
- **累加仍在正数域进行，最后取反**。这样 `INT_MIN`（-2147483648）在中间步骤 `x` 会溢出。见下面的遗留。

## 五、举一反三

### 自查清单：实现任何标准库函数时

- [ ] 我看过这个函数的**标准描述**（`man 3 xxx` 或 C99 草案），还是凭印象写的？
- [ ] 边界输入：空串、只有空白、只有符号、超长、溢出，各返回什么？
- [ ] 我的实现和 libc 在哪些输入上**不一致**？这些不一致有没有写在注释里？

最后一条是本次最想立的规矩：**简化实现是完全可以的，裸机上本来就不该背标准库的全部包袱。但简化必须写在注释里**，否则它就从"有意的取舍"退化成了"不知道的缺陷"。上游那份 `atoi` 的问题不在于简化，而在于**没写自己简化了什么**。

### 顺手体检 klib 的其他函数

本次复盘对 `string.c` 全部 11 个函数做了逐行核对，结论是**全部正确**（含 `strcmp` 用 `uint8_t` 提升做无符号比较、`memmove` 的重叠方向判断，都是对的）。

`stdlib.c` 剩下的：

- `rand()` / `srand()`：上游的标准 LCG，正确；
- `abs()`：`abs(INT_MIN)` 是 UB（`-INT_MIN` 溢出），和 libc 一致，不算 bug。

## 六、遗留（本次未处理）

1. **不检测溢出。** `atoi("99999999999")` 会静默回绕。标准 `atoi` 对溢出也是 UB，所以这不算偏离标准；真正需要检错的场合应该用 `strtol`——而 klib 目前没有 `strtol`。
2. **`INT_MIN` 无法正确解析。** `atoi("-2147483648")`：中间的 `x` 要先达到 `2147483648`，超出 `int` 范围。正确做法是在负数域累加（`x = x * 10 - (*nptr - '0')`）。没改是因为它会让主循环变复杂，而当前没有任何调用方需要 `INT_MIN`；**若将来 klib 加了 `strtol`，应当在那里一次做对，并让 `atoi` 变成它的薄包装**。
3. **没有 `atol` / `atoll` / `strtol` / `strtoul`。** 等有调用方需要再补。
