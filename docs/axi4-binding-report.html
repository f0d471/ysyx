2文件一：axi4.sv — AXI4 协议定义

这个文件是纯定义文件，不包含任何电路逻辑。它通过 `include "axi4.sv" 被其他模块引用，类似于 C 语言的头文件。

2.2 信号位宽参数

📄 axi4.sv · 第 10-18 行
// --- AXI4 参数 ---
`define AXI4_ADDR_W   32
`define AXI4_DATA_W   32
`define AXI4_ID_W     4
`define AXI4_LEN_W    8
`define AXI4_SIZE_W   3
`define AXI4_BURST_W  2
`define AXI4_RESP_W   2
`define AXI4_STRB_W   4

定义 AXI4 各信号的位宽。这些值直接来自 cpu-interface.md 规范：

  • ADDR_W = 32 — 32 位地址空间，覆盖 4GB
  • DATA_W = 32 — 32 位数据总线，与 RV32 的字长一致
  • ID_W = 4 — 4 位事务 ID，ysyxSoC 要求 arid[3:0]、rid[3:0] 等均为 4 位
  • LEN_W = 8 — 8 位 burst 长度，arlen[7:0]，值 0 表示单次传输（1 拍）
  • SIZE_W = 3 — 3 位传输宽度，arsize[2:0]，编码为 2^size 字节
  • BURST_W = 2 — 2 位 burst 类型
  • RESP_W = 2 — 2 位响应码
  • STRB_W = 4 — 4 位写选通，每 1 位对应 1 字节

2.3 Burst 类型常量

📄 axi4.sv · 第 20-23 行
// Burst 类型
`define AXI4_BURST_FIXED 2'b00
`define AXI4_BURST_INCR  2'b01
`define AXI4_BURST_WRAP  2'b10
常量值含义用途
FIXED00固定地址 burstFIFO 类设备
INCR01递增地址 burstNPC 使用这个，地址每次 +2^size
WRAP10回环地址 burstCache line 填充
💡 NPC 只用 INCR
当前 NPC 为多周期处理器，每次只发单次传输（len=0），burst 类型选 INCR 是最通用的选择。即使将来升级为流水线支持 burst，INCR 也够用。

2.4 响应码常量

📄 axi4.sv · 第 25-29 行
// 响应码
`define AXI4_RESP_OKAY   2'b00
`define AXI4_RESP_EXOKAY 2'b01
`define AXI4_RESP_SLVERR 2'b10
`define AXI4_RESP_DECERR 2'b11
响应码含义NPC 行为
OKAY (00)正常完成继续执行
EXOKAY (01)独占访问成功暂不使用（需要 LR/SC）
SLVERR (10)Slave 错误触发 Access Fault 异常
DECERR (11)地址译码错误触发 Access Fault 异常（地址不在任何设备范围内）
⚠️ 对应 B1 讲义中的 error 信号
SimpleBus 的 error 信号在 AXI4 中被编码为 rresp[1:0] / bresp[1:0]。非 OKAY 响应时，NPC 应触发 Access Fault（mcause=1/5/7）。

2.5 传输宽度常量

📄 axi4.sv · 第 31-34 行
// 传输宽度 (arsize / awsize)
`define AXI4_SIZE_1B   3'b000
`define AXI4_SIZE_2B   3'b001
`define AXI4_SIZE_4B   3'b010

arsize / awsize 编码为 2^size 字节。这是 AXI4-Lite 不具备的关键信号——它解决了 B2 讲义中提到的 UART 寄存器访问问题：

  • lb 指令 → SIZE_1B (000)，只访问 1 字节，不误触相邻寄存器
  • lh 指令 → SIZE_2B (001)
  • lw 指令 → SIZE_4B (010)，普通 32 位访问

2.6 通道结构体定义

AR 通道（读地址通道）

📄 axi4.sv · 第 38-45 行
// AR 通道 (读地址) - master 输出
typedef struct packed {
    logic [`AXI4_ID_W-1:0]    id;
    logic [`AXI4_ADDR_W-1:0]  addr;
    logic [`AXI4_LEN_W-1:0]   len;     // burst 长度 - 1
    logic [`AXI4_SIZE_W-1:0]  size;    // 每拍字节数 = 2^size
    logic [`AXI4_BURST_W-1:0] burst;   // burst 类型
} axi4_ar_t;
字段位宽NPC 设定值说明
id[3:0]4'h0事务 ID，NPC 固定为 0
addr[31:0]PC 或 ALU 结果读目标地址
len[7:0]8'h0burst 长度 = len+1 = 1 拍（单次传输）
size[2:0]3'b0102^2 = 4 字节
burst[1:0]2'b01 (INCR)递增地址模式

R 通道（读数据通道）

📄 axi4.sv · 第 47-53 行
// R 通道 (读数据) - slave 输出
typedef struct packed {
    logic [`AXI4_ID_W-1:0]    id;
    logic [`AXI4_DATA_W-1:0]  data;
    logic [`AXI4_RESP_W-1:0]  resp;
    logic                     last;
} axi4_r_t;
字段位宽来源说明
id[3:0]SoC 返回与请求的 arid 对应
data[31:0]SoC 返回读出的数据
resp[1:0]SoC 返回OKAY / SLVERR / DECERR
last1SoC 返回burst 最后一拍（单次传输时恒为 1）

AW 通道（写地址通道）

📄 axi4.sv · 第 55-62 行
// AW 通道 (写地址) - master 输出
typedef struct packed {
    logic [`AXI4_ID_W-1:0]    id;
    logic [`AXI4_ADDR_W-1:0]  addr;
    logic [`AXI4_LEN_W-1:0]   len;
    logic [`AXI4_SIZE_W-1:0]  size;
    logic [`AXI4_BURST_W-1:0] burst;
} axi4_aw_t;

结构与 axi4_ar_t 完全对称。AXI4 的关键设计之一：写地址和写数据使用独立通道，允许 Slave 提前知道写地址，即使写数据还没到，也可以先启动写操作的准备工作（如 DRAM 的行激活）。

W 通道（写数据通道）

📄 axi4.sv · 第 64-69 行
// W 通道 (写数据) - master 输出
typedef struct packed {
    logic [`AXI4_DATA_W-1:0]  data;
    logic [`AXI4_STRB_W-1:0]  strb;
    logic                     last;
} axi4_w_t;
字段位宽说明
data[31:0]写入数据
strb[3:0]写选通，每 1 位对应 data 的 1 字节。sb 指令只置 1 位，sw 置 4'b1111
last1burst 最后一拍（单次传输恒为 1）
💡 strb 对应 SimpleBus 的 wmask
strb[0]=1 表示写入 data[7:0]，strb[3]=1 表示写入 data[31:24]。与 SimpleBus 的 wmask 语义完全一致。

B 通道（写回复通道）

📄 axi4.sv · 第 71-75 行
// B 通道 (写回复) - slave 输出
typedef struct packed {
    logic [`AXI4_ID_W-1:0]    id;
    logic [`AXI4_RESP_W-1:0]  resp;
} axi4_b_t;

写回复通道只有 ID 和响应码，没有数据——写操作是单向的，Slave 只需告知"写成功/失败"。

2.8 默认值工厂函数

📄 axi4.sv · 第 111-139 行
function automatic axi4_ar_t axi4_default_ar();
    axi4_ar_t ar;
    ar.id    = '0;
    ar.addr  = '0;
    ar.len   = 8'h0;           // 单次传输
    ar.size  = `AXI4_SIZE_4B;  // 4 字节
    ar.burst = `AXI4_BURST_INCR;
    return ar;
endfunction

function automatic axi4_aw_t axi4_default_aw();
    // ... 结构相同
endfunction

function automatic axi4_w_t axi4_default_w();
    axi4_w_t w;
    w.data = '0;
    w.strb = 4'b1111;  // 默认全写
    w.last = 1'b1;    // 单次传输恒为 1

endfunction

三个工厂函数分别生成 AR、AW、W 通道的默认值。automatic 关键字确保每次调用都创建新的局部变量（综合为组合逻辑）。这些函数使得在需要构造默认 AXI4 事务时，可以用一行代码完成，而无需手动填写每个字段。

3文件二：axi_arbiter.sv — 仲裁器

这是三个文件中唯一的时序逻辑模块，包含一个 6 状态的状态机，负责将 IFU 和 LSU 的 SimpleBus 请求翻译为 AXI4 协议，并通过仲裁逻辑合并到一个 Master 端口。

3.1 模块声明与端口

📄 axi_arbiter.sv · 第 13-81 行
module axi_arbiter (
    input  logic clk,
    input  logic rst_n,

    // --- IFU SimpleBus 端口 (只读) ---
    input  logic [31:0] ifu_araddr,
    input  logic        ifu_arvalid,
    output logic        ifu_arready,
    output logic [31:0] ifu_rdata,
    output logic        ifu_rvalid,
    input  logic        ifu_rready,
    output logic [1:0]  ifu_rresp,

    // --- LSU SimpleBus 端口 (读写) ---
    // ... 读通道 (ar) + 写通道 (aw + w + b)

    // --- AXI4 Master 端口 (连接 SoC) ---
    // ... AR + R + AW + W + B 五通道
);

端口分为三组：

  1. IFU SimpleBus（第 17-24 行）— 只读，7 个信号：araddr、arvalid、arready、rdata、rvalid、rready、rresp
  2. LSU SimpleBus（第 26-44 行）— 读写，11 个信号：读通道 + 写通道（awaddr/awvalid/awready + wdata/wstrb/wvalid/wready + bvalid/bready/bresp）
  3. AXI4 Master（第 46-80 行）— 完整 AXI4，20 个信号：AR(7) + R(6) + AW(7) + W(5) + B(3)

3.2 状态机定义

📄 axi_arbiter.sv · 第 83-93 行
typedef enum logic [2:0] {
    S_IDLE  = 3'd0,
    S_RD_AR = 3'd1,  // 等 AR 握手
    S_RD_R  = 3'd2,  // 等 R 握手
    S_WR_AW = 3'd3,  // 等 AW 握手
    S_WR_W  = 3'd4,  // 等 W 握手
    S_WR_B  = 3'd5   // 等 B 握手
} state_t;

6 个状态覆盖了 AXI4 的所有握手阶段。读事务走 S_IDLE → S_RD_AR → S_RD_R → S_IDLE；写事务走 S_IDLE → S_WR_AW → S_WR_W → S_WR_B → S_IDLE。

3.3 锁存信号

📄 axi_arbiter.sv · 第 95-101 行
logic        sel_ifu;     // 1=当前服务 IFU, 0=服务 LSU
logic [31:0] addr_latch;
logic [31:0] wdata_latch;
logic [3:0]  wstrb_latch;
logic [1:0]  rresp_latch;
logic [31:0] rdata_latch;

仲裁器在 S_IDLE 时锁存请求方的信息。因为 SimpleBus 的请求信号只在 S_IDLE 时有效，进入后续状态后请求方可能撤除信号，所以必须在握手的瞬间锁存。关键信号 sel_ifu 记录当前服务的是 IFU 还是 LSU，用于在数据返回时路由到正确的接收方。

第 97 行 logic [31:0] addr latch; 中间有空格，应为 addr_latch。编译会报错，需要修复。

3.4 状态转移逻辑

📄 axi_arbiter.sv · 第 103-144 行
// --- 状态转移 ---
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n)
        state <= S_IDLE;
    else
        state <= state_next;
end

always_comb begin
    state_next = state;
    case (state)
        S_IDLE: begin
            if (lsu_awvalid)        // LSU 写优先
                state_next = S_WR_AW;
            else if (lsu_arvalid)   // LSU 读
                state_next = S_RD_AR;
            else if (ifu_arvalid)   // IFU 读
                state_next = S_RD_AR;
        end
        S_RD_AR: begin
            if (m_arready)
                state_next = S_RD_R;
        end
        S_RD_R: begin
            if (m_rvalid && m_rready)
                state_next = S_IDLE;
        end
        // ... 写通道类似
    endcase
end

仲裁策略：在 S_IDLE 中按优先级判断：

  1. LSU 写（lsu_awvalid）— 最高优先级，写操作不能延迟太久
  2. LSU 读（lsu_arvalid）— 其次
  3. IFU 读（ifu_arvalid）— 最低优先级

对于多周期 NPC，IFU 和 LSU 不会同时发请求，所以这个优先级实际上不会有冲突。但保留优先级逻辑是为了将来升级流水线时不用重写。

3.5 锁存请求逻辑

📄 axi_arbiter.sv · 第 146-174 行
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
        sel_ifu     <= 1'b0;
        addr_latch  <= 32'h0;
        wdata_latch <= 32'h0;
        wstrb_latch <= 4'h0;
        rresp_latch <= 2'b00;
        rdata_latch <= 32'h0;
    end else if (state == S_IDLE) begin
        if (lsu_awvalid) begin
            sel_ifu     <= 1'b0;
            addr_latch  <= lsu_awaddr;
            wdata_latch <= lsu_wdata;
            wstrb_latch <= lsu_wstrb;
        end else if (lsu_arvalid) begin
            sel_ifu    <= 1'b0;
            addr_latch <= lsu_araddr;
        end else if (ifu_arvalid) begin
            sel_ifu    <= 1'b1;
            addr_latch <= ifu_araddr;
        end
    end else if (state == S_RD_R && m_rvalid && m_rready) begin
        rdata_latch <= m_rdata;
        rresp_latch <= m_rresp;
    end else if (state == S_WR_B && m_bvalid && m_bready) begin
        rresp_latch <= m_bresp; // 复用存 bresp
    end
end

三个阶段的锁存时机：

  • S_IDLE — 在仲裁决策的同一周期锁存请求地址、写数据、写选通
  • S_RD_R — 读响应握手成功时锁存 rdata 和 rresp
  • S_WR_B — 写回复握手成功时锁存 bresp（复用 rresp_latch）

3.6 AXI4 Master 输出

📄 axi_arbiter.sv · 第 176-204 行
// AR 通道
assign m_arvalid = (state == S_RD_AR);
assign m_araddr  = addr_latch;
assign m_arid    = 4'h0;
assign m_arlen   = 8'h0;           // 单次传输
assign m_arsize  = `AXI4_SIZE_4B;  // 4 字节
assign m_arburst = `AXI4_BURST_INCR;

// R 通道
assign m_rready = (state == S_RD_R);

// AW 通道
assign m_awvalid = (state == S_WR_AW);
assign m_awaddr  = addr_latch;
// ... id/len/size/burst 同 AR

// W 通道
assign m_wvalid = (state == S_WR_W);
assign m_wdata  = wdata_latch;
assign m_wstrb  = wstrb_latch;
assign m_wlast  = 1'b1;

// B 通道
assign m_bready = (state == S_WR_B);

AXI4 五通道的输出逻辑。关键设计决策：

  • valid 只在对应状态为 1 — m_arvalid 仅在 S_RD_AR 时有效，符合 AXI4 规范：valid 一旦置 1，必须保持到握手成功
  • ready 只在对应状态为 1 — m_rready 仅在 S_RD_R 时有效，表示此时可以接收数据
  • 固定参数 — arlen=0（单次）、arsize=4B、arburst=INCR、wlast=1（单次传输恒为 1）

3.7 SimpleBus 回传输出

📄 axi_arbiter.sv · 第 206-223 行
// IFU
assign ifu_arready = (state == S_IDLE) && !lsu_awvalid && !lsu_arvalid && ifu_arvalid;
assign ifu_rvalid  = (state == S_RD_R) && m_rvalid && sel_ifu;
assign ifu_rdata   = m_rdata;
assign ifu_rresp   = m_rresp;

// LSU
assign lsu_arready = (state == S_IDLE) && !lsu_awvalid && lsu_arvalid;
assign lsu_rvalid  = (state == S_RD_R) && m_rvalid && !sel_ifu;
assign lsu_rdata   = m_rdata;
assign lsu_rresp   = m_rresp;

assign lsu_awready = (state == S_IDLE) && lsu_awvalid;
assign lsu_wready  = (state == S_WR_W) && m_wready;
assign lsu_bvalid  = (state == S_WR_B) && m_bvalid;
assign lsu_bresp   = m_bresp;

这是仲裁器的"反向"输出——把 AXI4 Slave 的回复翻译回 SimpleBus 格式，送回给 IFU 或 LSU。关键的仲裁逻辑在 ifu_rvalid 和 lsu_rvalid 的 sel_ifu 条件：

  • ifu_rvalid = ... && sel_ifu — 只有当前服务的是 IFU 时，才把数据返回给 IFU
  • lsu_rvalid = ... && !sel_ifu — 只有当前服务的是 LSU 时，才把数据返回给 LSU

4文件三：ysyx_250309.sv — 顶层包装

这个文件是 ysyxSoC 与 NPC 之间的"适配器"。它对外暴露 cpu-interface.md 要求的标准端口，对内连接 core 和 arbiter。

  2. IFU SimpleBus（7 线）— core 的取指端口 ↔ arbiter 的 IFU 端口
  3. LSU SimpleBus（17 线）— core 的访存端口 ↔ arbiter 的 LSU 端口
  4. debug（7 线）— 调试信号，ysyxSoC 不使用，但 core 有输出端口必须连接

4.5 Arbiter 实例化

axi_arbiter u_arbiter (
    .clk       (clock),

关键细节：第 191 行 .lsu_arvalid(lsu_arvalid & ~lsu_awvalid) — 当 LSU 有写请求时，屏蔽读请求。这是因为 core 的 LSU 在 store 指令时可能同时驱动 lsu_arvalid（因为 SimpleBus 的读写共用地址线），需要在 arbiter 入口处过滤。
