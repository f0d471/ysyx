1define.sv — 异常码常量 + 流水线字段

1.1 Access Fault 异常码

📄 define.sv · 第 88-91 行
`define TRAP_CAUSE_ECALL_M       32'd11   // M-mode ECALL 异常码
`define TRAP_CAUSE_IF_ACCESS     32'd1    // Instruction Access Fault
`define TRAP_CAUSE_LD_ACCESS     32'd5    // Load Access Fault
`define TRAP_CAUSE_ST_ACCESS     32'd7    // Store Access Fault

来自 RISC-V Privileged Spec 的 mcause 编码：

mcause 值异常名称触发条件
1Instruction Access Fault取指时 SoC 返回 rresp ≠ OKAY
5Load Access Faultload 时 SoC 返回 rresp ≠ OKAY
7Store Access Faultstore 时 SoC 返回 bresp ≠ OKAY
11M-mode ECALL已有，不变

1.2 流水线结构体新增字段

📄 define.sv · 第 101-106 行
//  IF → ID 通道 
typedef struct packed {
    logic [31:0] pc;
    logic [31:0] instr;
    logic        ifu_error;  // ← 新增
} if_id_t;
📄 define.sv · 第 130-132 行
    logic        inst_ebreak;
    logic        ifu_error;  // ← 新增
} id_ex_t;

ifu_error 需要从 IF 阶段传播到 EX 阶段，因为取指错误的异常需要在 EX 阶段触发（与 ECALL 同一位置），这样 trap 逻辑才能统一处理。

为什么 ifu_error 要过流水线？
ifu_error 在 IF 阶段（fetch.sv）产生，但该指令可能被 flush 掉（分支预测错误）。只有当指令真正到达 EX 阶段时，才应该触发异常。通过流水线寄存器传播，可以确保只在指令"生效"时才报告错误。

2.3 锁存逻辑扩展

📄 fetch.sv · 第 73-85 行
// 锁存响应数据
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
        instr_latch <= `INSTR_NOP;
        rresp_latch <= 2'b00;
    end else if (state == S_WAIT_RESP && ifu_respValid && ifu_respReady && !flush) begin
        instr_latch <= ifu_rdata;
        rresp_latch <= ifu_rresp;   // ← 新增：同时锁存响应码
    end else if (flush) begin
        instr_latch <= `INSTR_NOP;
        rresp_latch <= 2'b00;      // ← 新增：flush 时清除
    end
end

在响应握手成功的同一周期，同时锁存 ifu_rdata（指令）和 ifu_rresp（响应码）。flush 时两者都清除。

2.4 错误输出

📄 fetch.sv · 第 87-92 行
assign ifu_raddr     = pc_pointer;
assign ifu_reqValid  = (state == S_REQ) && !flush && !stall;
assign ifu_respReady = (state == S_WAIT_RESP) && !flush;
assign ifu_valid     = (state == S_DONE) && !flush;
assign instr_out     = ifu_valid ? instr_latch : `INSTR_NOP;
assign ifu_error     = ifu_valid && (rresp_latch != `AXI4_RESP_OKAY);  // ← 新增

ifu_error 仅在 ifu_valid（指令有效且未被 flush）且 rresp_latch ≠ OKAY 时为 1。这确保了只有真正"生效"的指令才会报告取指错误。

3mem.sv — 访存错误检测

3.1 新增端口

两个响应码输入：load 操作返回 rresp，store 操作返回 bresp。统一输出一个 lsu_error 标志。

3.2 响应码锁存

📄 mem.sv · 第 47-49 行
state_t state, state_next;
logic [DW-1:0] rdata_latch;
logic [1:0]    resp_latch;   // ← 新增

3.3 锁存逻辑扩展

📄 mem.sv · 第 76-85 行
// 锁存读数据
always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
        rdata_latch <= 32'h0;
        resp_latch  <= 2'b00;
    end else if (state == S_WAIT_RESP && lsu_respValid && lsu_respReady) begin
        rdata_latch <= lsu_rdata;
        resp_latch  <= is_load ? lsu_rresp : lsu_bresp;  // ← 关键：load 取 rresp，store 取 bresp
    end
end

关键设计：根据当前操作类型（load/store）选择锁存哪个响应码。load 操作的回复在 R 通道（rresp），store 操作的回复在 B 通道（bresp）。

3.4 错误输出

📄 mem.sv · 第 115-119 行
// 有访存操作且尚未到 DONE
assign lsu_busy = is_mem && (state != S_DONE);

// 总线错误
assign lsu_error = is_mem && (state == S_DONE) && (resp_latch != `AXI4_RESP_OKAY);

lsu_error 在访存完成（S_DONE）且响应码非 OKAY 时有效。由于 MEM 阶段在流水线中紧跟 EX，这个信号可以直接送到 execute 模块，无需过流水线寄存器。

4.2 异常优先级逻辑

📄 execute.sv · 第 147-161 行
// CSR 操作与异常响应
assign csr_raddr = csr_addr_in;
assign csr_wen   = inst_csrrw | (inst_csrrs & (rs1_addr_in != 5'b0));
assign csr_waddr = csr_addr_in;
assign csr_wdata = inst_csrrw ? op1_in : (csr_rdata | op1_in);

// 异常优先级：Access Fault > ECALL
wire access_fault = ifu_access_fault | lsu_access_fault;

assign trap_valid = access_fault | inst_ecall;
assign trap_pc    = pc_in;
assign trap_cause = ifu_access_fault ? `TRAP_CAUSE_IF_ACCESS :
                    lsu_access_fault ? (is_store_in ? `TRAP_CAUSE_ST_ACCESS
                                                    : `TRAP_CAUSE_LD_ACCESS) :
                    `TRAP_CAUSE_ECALL_M;

三目运算符实现了优先级编码：

  1. ifu_access_fault（最高）→ mcause = 1（Instruction Access Fault）
  2. lsu_access_fault → 根据 is_store 区分：mcause = 7（Store）或 5（Load）
  3. inst_ecall（最低）→ mcause = 11
为什么 Access Fault 优先级高于 ECALL？
在同一条指令中，如果同时触发了 Access Fault 和 ECALL（理论上不会发生），硬件错误应该优先报告。RISC-V 规范中，硬件异常的优先级高于软件异常。
